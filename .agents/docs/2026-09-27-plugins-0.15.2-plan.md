# plugins 0.15.2 与生态收敛方案

日期：2026-09-27。依据：`2026-09-27-versioning-assets-locale-and-galtranslpp-review.md` 及其后的讨论结论。

## 0. 目标

1. Qt 以上游版本 `6.11.1` 作为唯一版本键，消费方书写上游版本。
2. brotli 资源恢复规范文件名，GitHub 与 GitCode 逐字节一致。
3. GalTranslPP PR2 达到当前生态能力下的最佳形态：版本单点声明、可配置项有文档、emit 开销可解释且可测。
4. 需要 mcpp、xlings、xim glibc 改动的事项，以 issue 形式交给各自仓库。

非目标：修改 mcpp、xlings 或 glibc 配方本身。

## 1. 已确定的决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | Qt 只保留 `6.11.1` 键，删除 `6.11.1.1` | 该包无外部消费者；持有修正前载荷的只有两处 CI 缓存与本机沙箱，均可清除 |
| D2 | brotli 资源使用规范名，删除 `-r1` | GitHub 规范名已是修正内容；下载层按 sha256 校验缓存，同名替换安全 |
| D3 | Qt 的 GitCode 资源不删除 | Qt 归档来自 Qt 官方仓库及镜像；xlings-res/qt-base 仅含 QtQml 重打包，内容正确且仍被引用 |
| D4 | 就地修正与修订号的分界 | 包在索引中无外部消费者时就地修正；有外部消费者后用第四段修订号，直至 xlings 支持 `revision` |
| D5 | 版本单点声明，按需引用 | 版本写在工作区根一处；是否使用由成员的 build.mcpp 决定，声明只提供版本与载荷可见性 |

关键事实：`6.11.1` 与 `6.11.1.1` 共用同一配方体。因此在今天的索引上，全新安装的 `6.11.1` 已经是修正后的载荷。
D1 的索引改动只是删除冗余键；消费方的切换不依赖它先合入。

## 2. 工作项

### 2.1 xlings-res/brotli（无需 PR）

1. 向 GitCode 1.2.0 上传规范名资源 `brotli-1.2.0-linux-{x86_64,aarch64}.tar.gz`，文件取自 GitHub 规范名资源（sha256 `0b20a7cc…`、`07f52426…`）。
2. 两端 `SHA256SUMS` 改为规范名（GitHub 用 `--clobber`；GitCode 已由用户删除，直接上传）。
3. 两端逐字节核对。

### 2.2 xim-pkgindex：一个 PR

- qt、qt-base、qt-addons：删除 `6.11.1.1` 键及其说明注释，`latest` 指向 `6.11.1`；qt-addons 的依赖改为 `xim:qt@6.11.1`。
- brotli：URL 改回规范名，sha256 不变。
- 验收：xim CI 全绿；合入后等待索引发布，再用 `xlings info` 确认 `qt-base` 只列出 `6.11.1`。

### 2.3 mcpp-plugins 0.15.2：一个 PR

- `rules/qt.cppm`：缺少 SDK 时的提示改为 `"xim:qt-base" = "6.11.1"`。
- 测试 fixture（qt-consumer、qt-widgets-consumer）与 `docs/rules-qt.md`、README：版本改为 `6.11.1`。
- `ci.yml`：沙箱缓存 key 的前缀加代次（`mcpp-sandbox-v2-…`），`restore-keys` 同步修改。仅 fixture 哈希变化不够：现有 `restore-keys` 前缀会恢复持有旧 6.11.1 的缓存。
- 验收：三平台 CI 全绿。其中 Linux 的 widgets 打包检查要确认新缓存下装出的 `6.11.1` 带有运行时闭包（libdbus、xkbcommon、fontconfig），这正是 D1 的实证。
- 发布：tag v0.15.2、GitCode 镜像（sha256 比对）、mcpp-index 登记。

### 2.4 GalTranslPP PR2

| 项 | 内容 | 验收 |
|---|---|---|
| E1 版本 | `xim:qt-base` 改为 `6.11.1`；`mcpp.plugins` 改为 0.15.2 | CI 全绿 |
| E2 插件版本单点 | 根 `[workspace.dependencies] mcpp.plugins = "0.15.2"`，成员写 `{ workspace = true, features = [...], host-module = true }` | 构建通过；不支持时回退为逐成员声明，并记入 mcpp issue |
| E3 xlings 条目单点 | `xim:qt-base`、`xim:7zip` 移至根清单 `[target.windows.xlings.workspace]` | 成员构建程序中 rules-qt 事实为 `xlings: …/6.11.1`，7z.dll 仍在发布目录；不生效时回退并记入 mcpp issue |
| E4 文档 | `how-to-build.md`：Qt 6.11.1；以 `> 注:` 说明 `QT_ROOT_DIR`、vcpkg 的 `options.root`、`VCPKG_DOWNLOADS`、`VCPKG_DEFAULT_BINARY_CACHE`、`fast-release`，并注明：不使用 xim 的 Qt 时，注释掉 `xim:qt-base` 的声明，再设置 `QT_ROOT_DIR`，或在 build.mcpp 中以 `qt.root` 指定路径（声明即下载，属预期行为） | 评审 |
| E5 注释 | 修正成员清单中 7z 与 Qt 注释的错位（E3 成立时随之消失） | 评审 |
| E6 emit 测量 | CI 增加"再跑一次 emit"步骤并计时；首次 emit 加 `-v`，定位 5 条 "no Qt SDK" 警告的来源 | 得到第二次 emit 的实测时间与警告来源 |
| E7 缓存 | xpkgs 缓存 key 升级 | 日志显示 Qt 按 `6.11.1` 新装 |

E6 若查明警告来自插件（例如 rules-qt 在不需要 Qt 的构建程序中被调用），修正并入 0.15.2；否则记入 mcpp issue。

### 2.5 收尾

1. 索引发布后删除 GitHub 的 brotli `-r1` 资源（我），GitCode 的 `-r1` 资源由用户删除。
2. 删除本机沙箱中修正前的 Qt 载荷。
3. 更新两份评估文档与交付记录。

## 3. 顺序与依赖

```
2.1 brotli 资源 ──► 2.2 xim PR ──► 索引发布 ──► 2.5-1 删除 -r1
2.3 plugins 0.15.2 ──► 发布 + index 登记 ──► 2.4 GalTranslPP PR2
```

两条链互不阻塞：2.3 与 2.4 使用 `6.11.1` 键，该键今天已存在且内容已修正（见 §1 关键事实）。

## 4. 上游 issue（已提交，由上游决定处理方式）

| issue | 内容 | 是否阻碍开发 |
|---|---|---|
| mcpp-community/mcpp#710 | 宿主工具的子构建不使用其缓存键记录的工具链，首次 emit 额外安装 llvm@20.1.7 | 否：只增加首次耗时和磁盘占用 |
| mcpp-community/mcpp#711 | 发布物无法依赖另一个包按目标平台构建的可执行文件，只能借宿主工具边 | 否：本机构建结果正确；交叉编译时才会出错 |
| mcpp-community/mcpp#712 | `xpkg_dir` 把裸版本当字面 pin，xlings 则会匹配到四段版本键；已复现（libglvnd `1.7` → 装了 1.7.0.1，`xpkg_dir` 返回空） | 否：写精确版本键即可避开 |
| openxlings/xlings#620 | 配方修订号独立于版本号 | 否：没有外部用户时就地修正（D4） |
| openxlings/xlings#621 | glibc 载荷没有 locale 数据，编译进去的 locale 路径不在载荷内 | 否：只是一条提示；GalTranslPP 仅构建 Windows，不受影响 |

不再提交：设置 `QT_ROOT_DIR` 时仍下载声明的 Qt。这是预期行为，按 E4 写进文档。
视 E2、E3 的结果，可能再提交"xlings 条目支持从工作区继承"。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 删除 `6.11.1.1` 后，仍书写 `6.11.1.1` 的消费方解析失败 | 已知消费方只有 plugins fixture 与 GalTranslPP，二者均在本方案中改为 `6.11.1` |
| 某处缓存仍恢复出修正前的 `6.11.1` 载荷 | 两处 CI 缓存 key 均升级；Linux widgets 打包检查会在闭包缺失时失败 |
| E2 或 E3 不被 mcpp 支持 | 回退为逐成员声明，不阻塞发布 |
